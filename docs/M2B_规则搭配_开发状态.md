## 已交付

2026-11-04 配置交互修正：入口改为浅绿色「人数与菜数」按钮。弹窗编辑与应用分开；点完成才保存本次配置，点关闭取消。人数、菜数或季节范围变化后，清空旧菜单及推荐 ID／版本，显示重新搭配提示；未变化时保留原菜单。总菜数不在 1—20 时禁止完成。本次 planning 配置与手机草稿一起持久化，切换页面或重开不恢复旧配置，不改家庭默认。「本餐菜单」20 号字、菜名17号字，层级更明确。类型检查及4项隔离配置回归检查通过，真机已确认新按钮和标题显示；未代用户清空当前推荐菜单。

- 今日灵感的帮我搭配入口可按家庭默认生成菜单，支持本次人数与荤菜、素菜、汤数量覆盖，不写回家庭默认。
- 默认只使用所有主要食材均匹配当前季节或全年的菜。候选不足不自动放宽；用户可明确启用非当季／季节未设置食材，菜品标出缺口。
- 读取后端北京时间，按记录归属日期排除今天及前两天的已确认菜单。此规则沿用最新食记决策，覆盖旧设计文档中按确认时间的描述。
- 正式菜按 recipe_id 排除，同时以规范化名称和主要食材 ID 指纹排除同名同料复制菜；不同菜名但主料相同不直接视为同一道菜。
- 隐藏、已删除菜谱和含隐藏／删除主料的菜不自动推荐；食材季节未知不默认为全年。
- 在满足分类配额、无重复前提下，以季节覆盖、主料多样性和小幅随机排序组合整桌；硬菜是附加标签，不重复计数。
- 支持只换一道，其他菜快照不变。成功换掉的菜及其指纹记为本餐拒绝项，不在后续替换中回来。替换失败保留当前菜单并说明原因。
- 支持整桌换一套；只有一套合法组合时明确说明，没有用重新排序伪装新菜单。
- 推荐有服务端 ID 和版本；生成及变更请求带稳定请求键处理网络重试。过期版本不能继续换菜或确认。
- 确认前在短写事务中重新检查近期记录、当前季节及菜谱是否改变；确认写入原有食记，同推荐不能重复确认。菜单人数允许在核对页显式调整，不自动换算用量。
- 真正手动增删菜品会转为自己挑方式，按已确认决策允许主动重复；仅切换两个入口不改变菜单。
- 菜单核对页提供采购清单。按主要食材 ID 去重；用量全部有记录且单位相同才用 Decimal 相加；缺量或不同单位显示说明，不推算克数、不换算单位。
- 更正食记时，采购清单复用历史快照，菜谱被删除后旧记录仍可查看。

## 数据与接口

新增 Alembic `0004_rule_plans`。正式库在升级前已使用 SQLite backup 备份到 `.cache/db-backups/eating-before-rules-20261104-213103.db`。已有菜谱、食记及家庭配置保留。

`rule_plans` 保存本次人数与构成、菜品快照、拒绝项、季节扩展许可、日期、版本、幂等键及确认后的食记 ID。推荐草稿与已确认食记分开，未确认不影响三天避重复。

- `POST /api/v1/recommendations`：request_key、可选人数／分类数量覆盖、allow_nonseasonal。
- `GET /api/v1/recommendations/{id}`：读取当前版本。
- `POST /api/v1/recommendations/{id}/replace`：目标菜 ID、expected_revision、request_key。
- `POST /api/v1/recommendations/{id}/regenerate`：整桌重选。
- `POST /api/v1/shopping-list`：所选菜 ID；更正历史时附记录 ID 及版本。
- 原确认接口增加可选 plan_id／plan_revision，两个字段必须一起提供。

上述接口使用原有家庭鉴权和短事务，不包含外部模型调用。

## 当前边界

本阶段是零模型调用的规则推荐。没有自然语言输入、口味或禁忌语义判断，也不会生成新菜来虚构候选充足。下一阶段接入真实 LLM 后，再实现对话、保留指定菜、定向补菜与临时菜主动保存。

开发包仍依赖 Metro 和后端，本阶段不需要重新安装 APK。
