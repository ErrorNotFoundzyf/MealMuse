网络异常时自动进入规则模式，支持“帮我搭配”“换掉菜名”“换第一道”“不吃牛肉”和“今天想吃一道硬菜”等明确指令。已有禁忌、硬菜数量、季节和三天避重复继续校验；已有语义偏好时只使用此前已评估且事实未变化的候选。复杂或有歧义的要求会保留菜单并提示，不冒充模型理解。若菜谱不足也会明确提示。恢复网络后对话自动继续使用 DeepSeek。

日期：2026-11-05；服务版本 0.4.0。代码、迁移和联调已完成，用户真机业务验收待进行。沿用现有 Android 调试安装包，无须重新构建 APK。本次追加两级候选与固定菜单方案，替代下文早期“按钮触发对话”的行为。

## 两级候选与固定菜单更新

用户已确认：程序按季节、分类、近期记录等得到候选1；模型按本餐个性化要求筛选为候选2，按分类保存在本餐状态。初始菜单和后续按钮换菜都只能引用这批已评估的菜。只有用户发送对话或主动重试对话才访问模型，成功重新筛选后替换候选2。

- 模型的挑菜响应同时包含 `eligible_ids` 和当前菜单选择；只评估过且通过校验的 ID 才进入候选2。未发送给模型或未被接受的菜不能作为按钮备选。本轮候选1先按相关分类和季节排序，送出至多 60 道非保留菜及至多 20 道保留菜；超过这一批的菜不能视为已评估。
- 临时菜仍由主动对话提出，经过原食材、季节、分类、禁忌和重复校验，可作为本餐候选2成员；按钮不会自行生成新菜。
- 候选2持久保存菜品事实快照、条件版本及人数菜数。按钮不创建模型客户端，不追加聊天消息；按分类、去重和主料多样性挑选，保留非目标菜快照。
- 每次按钮操作重新检查食材季节、近期确认记录、隐藏/删除及菜谱内容；菜谱改变后的候选需要再次对话评估，不能用旧的模型判断替代新事实。
- 单道换菜拒绝原目标；整桌换菜要求各道都换成其他备选。只有成功换菜才更新拒绝集合。备选不足、过期或正在等待澄清时保留旧菜单，明确提示，不隐式扩大到候选1或自动请求 AI。
- 手动调整和配置变更后，先通过对话同步并重新评估。旧版没有候选2的 AI 菜单提示先发送要求；不会把旧候选1伪装成模型已评估结果。
- 输入模型的理解阶段改为菜单 ID、名称、分类及食材名称/别名；挑菜阶段保留配方事实，去除数量和重复展示字段。每轮记录真实 `usage` 中的输入、输出、缓存命中及请求数，不凭估计宣称节省比例。
- 菜单移出聊天滚动区域并固定在顶部，标题 17、菜名 15、同行分类 12；更多操作收纳整桌换菜与重新对话。菜单可收起，键盘弹出时自动显示摘要；菜多时列表高度受限并可滚动，聊天记录独立滚动。

验证：全部 **102 项后端测试与前端类型检查通过**。新增测试用禁止构造模型客户端的方式验证按钮调用为零，并覆盖候选2范围、幂等/过期版本、耗尽不改菜单、整桌替换、新对话换池、菜谱/季节/近期记录变化。

真实 DeepSeek 联调：一次对话筛得 4 荤、3 素、3 汤，生成 1 荤 1 素 1 汤；随后按钮将香菇炖鸡换成萝卜炖排骨，其余两道、聊天消息和候选2版本不变。本次对话两次模型请求合计输入 4835 tokens、输出 405 tokens，其中缓存命中输入 512 tokens；按钮换菜调用为零。该数值只代表这一次测试，不代表固定用量或成本下降比例。真实测试没有确认食记或修改正式菜谱。

真机已检查紧凑固定菜单与同行分类布局；旧手机选菜未被覆盖。

后续同日 UI 更新：固定菜单改为横向无图文字卡片，分类使用与库列表一致的淡色标签；详见 [横向菜单与标签配色](ui/横向菜单与标签配色.md)。该更新替代上文纵向紧凑列表布局，候选与模型规则保持不变。

### 硬菜识别修复

2026-11-05 用户报告直接输入「今天想吃一道硬菜」后，模型把普通荤菜称为硬菜。原因是模型上下文遗漏 `is_hearty`，本餐缺少整桌硬菜数量校验。

- 现在理解和挑菜阶段均传入真实硬菜标签，硬菜不等同于荤菜，也不按菜名猜测。一个菜的主分类和硬菜标签分别处理。
- 「想吃一道硬菜」沿用当前荤、素、汤配置及总菜数，在其中恰好包含 1 道有硬菜标签的菜；即使模型把硬菜数量误写为荤菜配额，程序也不会据此覆盖原配置。硬菜数量单独保存在本餐记忆，不修改家庭默认。
- 初次结果、单道按钮替换、整桌替换、后续对话及最终确认都复验硬菜数量；标签改变后旧判断失效。备选中没有足够的有效硬菜时明确不足，不把普通荤菜或没有库内硬菜标签的 AI 临时菜充当硬菜。
- 硬菜数量说明按真实菜单标签生成，避免模型把未标记菜称为硬菜。可以明确说「不要硬菜」改为 0 道，或「硬菜数量不限」移除该数量要求。
- 「人数与菜数」「自己调整」「确认菜单」按钮高度由 44 调整为 36，字号保持 13，点击区域通过 hitSlop 适当扩展。

验证：全部 109 项后端测试及前端类型检查通过；新增 7 项覆盖标签传递、直接对话、普通荤菜冒充硬菜、硬菜不足、素菜附带硬菜标签、零模型按钮换菜保留配额、确认复验和明确修改数量。最终说明文案与配额保护又运行了这 7 项针对性回归。

真实复测直接发送「今天想吃一道硬菜」，得到 2 荤 1 素 1 汤，水煮鱼片标为「荤菜 · 硬菜」，其余三道未标硬菜；随后规则按钮替换为另一道带硬菜标签的菜，整桌仍恰好 1 道硬菜。没有修改正式菜谱标签或确认测试食记。

## 已实现

- 「帮我搭配」提供底部输入框、用户及助手消息、当前菜单、失败重试、重新对话。
- 模型先理解人数、菜数、偏好、禁忌与替换对象；服务端 SQL 检索候选，再由模型挑菜、组合或补充临时菜。JSON 输出经过结构和业务校验才发布。
- 规则独立检查分类配额、食材 ID、季节、三自然日硬排除、重复菜、已知禁忌及版本；生成期间不占用数据库写事务，落库前再次校验。
- 指定两道换菜时，其他菜的名称、主要食材和做法快照保持不变。替换成功的旧菜保留在本餐拒绝集合，不因下一轮聊天自动恢复。
- 本餐结构化条件、偏好、拒绝项和最近 20 条消息持久化；模型使用最近 6 条消息及结构化状态。最多保留 4 条待处理要求，失败不会静默丢弃新限制。
- 手动选菜后继续聊天会传入最新菜单；手动主动重复仍允许，但保留本餐明确禁忌。调整人数或菜数会清空旧菜单、保留本餐条件；「重新对话」明确清空本餐条件与未确认菜单。
- 不隐式建立长期画像；家庭默认、菜谱与已确认食记继续作为持久数据，无向量库或额外 RAG 框架。
- AI 临时菜仅含菜名、分类、已知主要食材，不编造做法或克数。不自动进入菜谱库，可主动保存；也可直接确认到食记快照和采购清单。
- 当前菜谱可能缺少完整调味及做法。存在硬限制时显示确认核对提示，必须主动勾选；已知冲突仍阻止确认。核对提示不代表算法能保证未记录的配料不存在。

## 配置与接口

真实密钥仅在本地 `backend/llm.local.json`，该路径已 Git 忽略。仓库示例 `backend/llm.local.example.json` 的密钥为空。后端进程变量 `DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL` 可覆盖文件。

本次采用 `https://api.deepseek.com`、`deepseek-flash`，关闭模型思考，使用 JSON 输出。实现参考 DeepSeek 官方 [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/) 和 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。

| 接口 | 行为 |
| --- | --- |
| GET `/api/v1/ai/status` | 是否已配置、服务商、模型；不返回密钥 |
| POST `/api/v1/ai/chat` | 理解并处理本轮要求，返回当前菜单及对话状态 |
| POST `/api/v1/ai/plans/{id}/save-temporary` | 主动保存临时菜，并更新菜单版本 |
| POST `/api/v1/meal-records` | 沿用原确认接口，增加配料核对与手动调整标记 |
| POST `/api/v1/shopping-list` | 可使用推荐菜单 ID/版本解析临时菜 |

迁移 `0005_ai_memory` 为 RulePlan 增加 JSON 记忆字段；旧规则菜单兼容。真实数据库已在迁移前备份到本机 `.cache/db-backups/`，未提交 Git。

每次用户主动发送对话通常两次模型调用，分别理解和筛选搭配；歧义或闲聊可仅理解。按钮换菜为零次。空输出或结构不合法最多修正一次，每轮总计不超过 4 次调用；连接中断、鉴权失败、余额不足和限流返回明确提示。模型请求不包含密钥以外的认证材料，异常不回显上游请求内容或密钥。当前模型调用预算为 42 秒，手机等待 50 秒。

## 用户验收步骤

1. 在「今日灵感 → 帮我搭配」底部输入家常口味及本餐要求，检查人数、菜数和季节提示。
2. 说「换掉第一道和汤，另外两道保留」，检查只替换目标菜。
3. 增加本餐忌口，再连续换一道，检查要求保留；不能识别的限制应追问或阻止确认。
4. 切换自己挑，手动调整，再回到对话继续，检查模型接收到最新菜单。
5. 如出现 AI 临时菜，确认未主动保存时不会出现在菜谱库；主动保存后可正常编辑。
6. 确认最终菜单，在食记查看同日期的菜品快照；确认后近期菜进入 AI 硬排除。
7. 网络故障时检查旧菜单保留、待处理要求可重试，未完成的要求不能直接确认。
